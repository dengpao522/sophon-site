ULM · AUDITABLE COGNITIVE LEDGER

从长期记忆算法到可审计认知账本

一份把 ULM 推入「可审计信任赛道」的完整升级：理论依据、数据模型变更、验证机制、结构化审计输出与实施路线图。

CORE VERDICT · 核心结论

ULM 不需要转型，需要升维。四个核心机制与可审计推理的要件逐一同构，缺的只是三块板：独立验证器、连续置信度、结构化审计包。补齐之后，ULM 从「记不住的问题的解法」变成「可信 AI 的记忆底座」。

02 / THEORY ALIGNMENT

理论对齐：六项要件，四项同构、两项缺口

把可审计推理的要求逐条拆开，与 ULM v1 现状对照。结论：缺口清单就是升级清单，且全部是在现有骨架上增量实现。

可审计推理要件ULM v1 现状判定
① 显式认知账本：假设、置信、证据、未决问题全部落账、不可篡改 L1 事件账本为不可变 append-only 原始流，可审计 / 可回放 / 可重蒸馏；语义层版本化，supersedes 不涂改。 骨架同构
② LLM 只当 System 1，裁决权在外部确定性机制 「LLM 只抽候选，状态机由代码执行，LLM 无权裁决」的工程铁律。 完全一致
③ 知识与推理分离，不能糊在神经权重里 记忆外置，模型 / 领域 / 厂商解耦——三条不可让渡原则之一。 完全一致
④ 证据不足宁可拒答，不编造 vigilance 拒答：证据与查询重叠率不足时显式拒答。 完全一致
⑤ 信念更新必须经独立验证，验证不过不得改写既有信念 trust 标签存在，但打标无独立验证器背书；版本裁决不校验 trust，未验证候选可能覆盖已验证事实。 缺口① · 无验证器
⑥ 答案可审计：每步推理引用可复查的证据链 provenance 来源事件 ID 已存在，但缺少连续置信度、验证依据字段与结构化「审计包」输出。 缺口②③ · 字段与审计包
缺口①②③全部是加字段、加接口、加前置条件，不推翻任何既有设计；旧记忆节点无需迁移即可在新版本下运行。
03 / TECHNICAL UPGRADE

技术升级：五项变更，全部向后兼容

按「数据模型 → 验证器 → 裁决规则 → 输出接口 → 维护流程」的顺序展开。

3.1 · 数据模型新增 κ、v 两字段

节点元组由 m = (c, e, t_v, L, σ, 𝓛, π, η) 扩展为 m′ = (c, e, t_v, L, σ, 𝓛, π, η, κ, v)。

κ

连续置信度（confidence），κ ∈ [0,1]

trust 标签的数值化，用于检索加权与审计评分。缺省时由 trust 映射。

verified → 0.9  ·  inferred → 0.5  ·  disputed → 0.3
v

验证记录（verification record）

回答「凭什么可信」的质检报告，与回答「从哪来」的 provenance 明确区分。包含五个分量：

  • verdict：verified | unverified | refuted | stale
  • method：retrieval | rule | exec | tool | human
  • checked_at：最近验证时间戳
  • evidence[]：验证依据（外部引用 URL/DOI、规则 ID、执行输出摘要）
  • verifier_id：验证器标识与版本（审计可复现的前提）
π vs v.evidence：π 回答「这条记忆从哪来」（出生证明），v.evidence 回答「凭什么可信」（质检报告）。审计需要的是后者，ULM v1 只有前者。

3.2 · V 层独立验证器：三类内置检查

在写入路径与读取路径之间插入验证器层，全部为确定性或半确定性检查，LLM 无权出具 verified 结论。

rule-check

确定性规则与约束校验：内部一致性、时间区间合法性、单位与量纲检查。

全部记录 · 毫秒级

retrieval-check

对外部权威源（官方文档、API、检索）做证据比对：命中即 verified，矛盾即 refuted。

事实类 · 百毫秒级可异步

exec-check

代码执行 / 工具调用实测：日期推算、数值计算、接口核验。

可计算事实 · 秒级挂睡眠期
分级验证策略（控制成本）：高价值事实（参与裁决、被高频检索、access=confidential）执行完整验证链；日常记录仅 rule-check 加异步 retrieval-check。验证是稀缺资源，按审计价值分配。

3.3 · I5 版本裁决的「验证门」

八类关系状态机不变，仅在 supersedes 动作前加一道前置检查。

// I5 状态机执行前的验证门（新增）
if candidate.κ < incumbent.κ
   and candidate.trust != verified
   and incumbent.trust == verified:
      // 未验证的新信息不得覆盖已验证的现行事实
      relation(supersedes) → relation(contradicts)
      candidate.σ = disputed   // 挂起，等待验证
      incumbent.σ = active     // 现行事实保持有效
      // 入 M6 队列：异步触发 candidate 的 re-verification
争议不再只是双向标记，而是低信任方被自动挂起、高信任方守住阵地——这是「信念只在独立验证过的证据支持时才被修订」的状态机表达。

3.4 · R4–R5 输出结构化审计包 audit_bundle

把散落在每条记忆里的溯源信息，升级为一次一个结构化审计对象，供审计员、监管方与调用方复查。

answer_id

答案标识。

citations

引用的记忆节点（版本精确），每条含 node_id、version、trust、κ、σ、t_v、𝓛。

provenance

回溯到 L1 原始事件流（event_id 列表）。

verification

每条引用的验证状态与依据（v 记录）。

confidence_path

κ 的融合方式，供复核加权是否合理。

refusal

null，或 { reason, threshold }——若触发 vigilance 拒答。

有了审计包，「错在推理、证据还是假设」第一次可定位：引用全 verified → 推理端；某条 unverified/refuted → 证据端；无引用且未拒答 → 假设端。

3.5 · 新增 M6：信任维护（验证状态不是终态）

信任衰减

长期未复核的 verified 记录，κ 随时间缓慢下调，跌过阈值即进入 re-verification 队列。

争议促验

持续 disputed 的记录对，在睡眠期触发异步 re-verification，结果落地为 v 记录并更新 κ。

评测扩展

新增审计覆盖率与错误可定位率两项指标，作为对外讲述的数据基础。

05 / METRICS

两项审计评测指标

不编造基准分数，用可复现、可审计的口径衡量自身。

审计覆盖率
答案中引用条目携带完整 v 记录的比例。
错误可定位率
注入错误后，审计包能否把错误准确归因到证据端。
口径边界：可审计记忆 ≠ 可审计推理。对外纪律是「可审计推理需要可审计记忆，我们是那块地基」，不越界声称解决了推理本身。
